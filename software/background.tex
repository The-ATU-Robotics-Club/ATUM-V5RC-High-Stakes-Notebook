\section{Robot Disambiguation}
Because VURC involves the creation of two robots, we are programming for two robots (of course). We preferably want to reuse as much code as feasible between the two robots. Not only will this make the task at hand more manageable, but more robust: it is easier to catch problems and debug if we essentially have two machines to test with. To this end, our project is designed to be compiled and uploaded to both robots. 

We could have accomplished this with templates, but decided against this as we preferred that updates for the 15" API are concurrently performed with the 24" API; i.e., they are one in the same. If we made use of templates, we would have to work on the 15" as a base, save the template we produce, and update the version for the 24". Preferably, the two bots share all the same files. 

We've previously made use of jumper cables to dynamically setup the robots upon initialization during Over Under. During the disabled period, the robot would check if a jumper cable was placed in a specified ADI port and would setup accordingly. 

To avoid the need for a jumper cable and clear up that ADI port, we swapped out the jumper cable for a file on the Brain SD card. The same logic applies: the robot would check if the file associated with the 15" was present and setup the program for the 15" if it was found, otherwise it would setup for the 24". 

This still required another piece of hardware (the SD card), though, so we preferably wanted a solution that relied on the least additional number of components, zero. 

To this end, we make use of the unique Brain ID present on all VEX V5 Brains. This value is normally inaccessible in programs, so we have to find this ID and inject it into the program somehow. To this end, we make use of the PROS client to find the Brain ID with the 
\begin{lstlisting}[language=bash]
pros v5 status
\end{lstlisting}
command. After this, we make use of preprocessor definition statements to allow the program to adjust setup upon compilation. 

This means that, depending on which robot is currently connected, the compiled program delivered to the brain is changed to accommodate its unique setup. 
\begin{lstlisting}[language=bash]
# Gets the unique ID for the currently wired brain, or zero otherwise.
# This is accessible in code as the preprocessor definition BRAIN_ID. 
BRAIN_ID:=$(shell pros v5 status | grep -ohZ "0x[0-9a-e]*" || echo 0)
$(info Brain ID is $(BRAIN_ID))
$(shell rm bin/main.cpp.o) # Forces main to rebuild to update brain ID. 
CPPFLAGS=-D_POSIX_THREADS -D_UNIX98_THREAD_MUTEX_ATTRIBUTES -D_POSIX_TIMERS -D_POSIX_MONOTONIC_CLOCK -DBRAIN_ID=$(BRAIN_ID)
\end{lstlisting}

\section{GUI}
In years past, the GUI for our team has been lacking. This doesn't just have aesthetic consequences, while, yes, it is nice for the screen to have pleasant visuals, there is a whole means of debugging, tuning, and error-handling that we just aren't using. 

Before Over Under, we would simply make use of the LCD template that PROS ships with. This works for simple autonomous routine selectors and debugging purposes, but is rather limited. 

Last year, we began to experiment with LVGL \cite{bib:lvgl} for our selector. Just a handful of buttons, but a marked transition from years prior. 

This year, we wanted a GUI with the following features: 
\begin{itemize}
    \item A routine selector.
    \item A logging utility.
    \item A graphing utility.
    \item A map visual. 
\end{itemize}
These are common features across GUIs implemented in VEX, each with obvious benefits. Further, we want a home screen to display our logo and an error screen. Additionally, the routine selector should only need routines to be modified in one place; in Over Under, adding a routine involved changing around four different disparate sections of the project. 

The development of the screens themselves was fairly straightforward: we made use of a LVGL simulator \cite{bib:lvglsim} to create each screen separately. For the sake of simplicity and a consistent color palette, we borrowed the color scheme from the image editing program GIMP \cite{bib:gimp} for our own GUI. 

After each screen was developed, the code was broken up into classes, with a Screen class holding those variables and helper methods shared and used by all screens. Alongside this structure, the interface between the GUI and the rest of the program was developed (the ability to add lines to the log, points to the graph, etcetera). 

The most technically challenging section of the GUI was the matter of consolidating routines into a single location. To this end, in our interface for the robots, a virtual private method for initializing the routines is added. This method will involve populating two other private members, one for the behavior associated with the autonomous routines and one for their names. Using preprocessor macro statements, we can make this entire process seamless. 
\begin{lstlisting}[language=C++]
/**
 * @brief Creates space within which to place the routine definitions the robot
 * will run and the GUI will display.
 *
 */
#define ROUTINE_DEFINITIONS_FOR(robot) void robot::initializeRoutines()

/**
 * @brief Begins an autonomous routine definition. The name parameter will be
 * what is displayed by the routine selector on the GUI.
 *
 */

#define START_ROUTINE(name)                                                    \
  if(!routineNames.empty()) routineNames += '\n';                              \
  routineNames += name;                                                        \
        routines.push_back( \
            [this]() {
/**
 * @brief Ends an autonomous routine definition.
 *
 */
#define END_ROUTINE                                                            \
  });
\end{lstlisting}

In order to force this method to run, we explicitly delete several default-generated constructors and make use of a pattern called Curiously Recurring Template Pattern (CRTP) \cite{bib:crtp}. 
\begin{lstlisting}[language=C++]
// These are deleted to force the use of the templated constructor.
Robot() = delete;
Robot(const Robot &) = delete;
Robot(Robot &&) = delete;

/**
 * @brief Constructs the Robot by calling its children's initializeRoutine
 * method. This essentially stores the routine information for future use (and
 * tells the GUI to begin loading).
 *
 * @tparam SpecRobot
 * @param spec
 */
template <class SpecRobot>
Robot(SpecRobot *spec) {
    spec->initializeRoutines();
    GUI::Manager::startLoading(spec->getRoutineNames());
}
\end{lstlisting}
This allows the straightforward adjustment of our routines all in one location, the autonomous file for the robot in question: 
\begin{lstlisting}[language=C++]
ROUTINE_DEFINITIONS_FOR(RobotClone) {
  START_ROUTINE("Skills")
  END_ROUTINE

  START_ROUTINE("Test A")
  END_ROUTINE
}
\end{lstlisting}

\section{Wrappers and Error Handling}
Wrappers around PROS devices are omnipresent throughout our code. These serve several purposes, depending upon the device being wrapped. In the case of the Odometer class, for instance, a three wire encoder is encapsulated with the logic to get proper readings from the AMT102-V encoders we use and to find distance traveled. 

Some wrappers are more plain, for instance the optical sensor is wrapped to support returning an enumerated value for the color read, indexing, and proximity detection. As with all smart devices, there is also support for dynamic initialization: where the port of the device is determined at runtime, rather than given explicitly. 

Overall, the wrappers provide simpler application for the use cases we have. Another critical purpose these wrappers serve is error handling. Many device wrappers are equipped with a "check" method (or equivalent) that provides basic diagnostics. 

In the case of motors, for example, we can detect if motors are overheating or if they are not connected. In the case of line trackers, we can check if the reading is above a "baseline" expected value to see if it is functional. We can even test limit switches by pressing them during initialization to ensure they are functioning. 

\section{Tasks}
Tasks are more or less threads in the context of PROS. Essentially, actions that occur in the background to normal processes. Tasks are important for constructs like odometry, where we would prefer that the tracking occur \textit{in the background} of the other work we are performing. Or even for printing to the remote, where updates require specific pauses in between commands. 

While it is possible to avoid tasks, they can simplify the program significantly if used appropriately. There are three primary concerns with tasks:
\begin{itemize}
    \item Overuse, leading to increased complexity.
    \item Lack of a pause in a task loop, leading to CPU-hogging. 
    \item Managing global, mutable state among several tasks, leading to unexpected behavior. 
\end{itemize}
Overuse is mitigated by plain restraint. Similarly, adding pauses to loops like:
\begin{lstlisting}[language=C++]
while(true) {
    ...
    wait(); // This is to allow other tasks to run!
}
\end{lstlisting}
is maintained by discipline (it helps that issues that stem from this are typically obvious and easily corrected). The last issue can typically be avoided, isn't too serious, or, failing that, can be managed using a mutex.  

The way tasks are typically created in PROS is using a particularly procedural technique, where a task is created as such:
\begin{lstlisting}[language=C++]
void taskFn(void*) {
    while(true) {
        std::cout << "Hello world!\n";
        pros::delay(10);
    }
}

void opcontrol() {
    Task task{taskFn, "Example Task"};
}
\end{lstlisting}
Preferably, when we create an object like an arm or odometry system, a task is created upon construction. To this end, we use a method created by fellow competitors, the earliest reference to which we are aware of is from team 7842F during Turning Point (their website seems to have been removed, unfortunately, but it listed a similar concept we discuss here) \cite{bib:theotasks}.

We created an interface class called Task that uses CRTP in a similar manner to our GUI to make use of a method called prepBackgroundTasks defined by its derivatives. This method will populate a vector of parameters to create PROS tasks. When it comes time to start the background tasks, startBackgroundTasks is called on odometry, or the arm, or whatever the system in question is and another vector of unique pointers to PROS tasks is populated based on the given parameters. 
\begin{lstlisting}[language=C++]
void Task::startBackgroundTasks() {
    // If the tasks have already started, don't try to start them again.
    if(tasks.size()) {
        return;
    }
    for(TaskParams params : taskParams) {
        auto task = std::make_unique<pros::Task>(params.taskFn,
                                                 params.priority,
                                                 TASK_STACK_DEPTH_DEFAULT,
                                                 params.name.c_str());
        tasks.push_back(std::move(task));
        taskLogger.debug("Task \"" + params.name + "\" with priority " +
                         std::to_string(params.priority) + " has started.");
    }
}
\end{lstlisting}

The trick is that the task functions provided to the PROS task constructor are function objects stored in the parameters we collected for each task.  See this snippet from the protected part of the Task interface:
\begin{lstlisting}[language=C++]
struct TaskParams {
    const std::string name;
    const std::uint32_t priority;
    const std::function<void()> taskFn;
};

std::vector<TaskParams> taskParams;
\end{lstlisting}
We also ensure that the prepBackgroundTasks method is called by strategically deleting the default constructors of Task and calling the method in its single constructor.
\begin{lstlisting}[language=C++]
Task() = delete;
Task(const Task &) = delete;
Task(Task &&) = delete;

template <class TaskHandler>
Task(TaskHandler *handler,
     const Logger::Level loggerLevel = Logger::Level::Info) :
     handlerName{handler->getHandlerName()},
     taskLogger{loggerLevel} {
    handler->prepBackgroundTasks();
    taskLogger.debug("Tasks associated with " + handlerName +
                     " have been prepared to start.");
}
\end{lstlisting}

This class allows us to associate Tasks intimately with the objects they work with. Additionally, it allows us to associate an arbitrary number of tasks (up to the limit of concurrent tasks) with said objects. Further, its usage is made simpler via preprocessor macros, similar to the macros for the Robot interface.

\subsection{State Machines}
Finite state machines are a class of automata that are defined by states and transitions between them (the strict definition is more rigorous, but irrelevant for our purposes). State machines are conceptually valuable in robotics for modeling the states of the subsystems of our robot.

In the case of the ladybrown, we can model the behavior of the ladybrown in terms of states: loading, scoring, resting, and so on. We can also use a simple switch statement to associate various behaviors with each state. 

In short, state machines provide an excellent method of organizing the state and behavior of our subsystems.

\subsection{Motion Profiling}
For movements, we could simply use PID to drive the current position of a system to a desired reference position. This works in many circumstances, but could be improved upon. Rather than blindly applying a voltage based on error, we can instead take into account the physical parameters of the system: that is, max velocity, acceleration, and jerk. 

This is the idea behind motion profiling: instead of telling the system to go to the end position, we essentially plan out the entire motion for it to get there. This will lead to smoother movements as well as potentially reduce the amount of oscillations the system experiences. As a bonus, the parametrization aspect of this process can provide us with useful information, like how long we should expect the system to take to get to our target. 

This can be accomplished in a few ways. The most apparent approach would be to populate a vector with the points along the profile according to the constraints. Then going back through the vector in a forward and backward pass to make sure that max acceleration and jerk are obeyed at each step. Potentially adding another pass for timestamping. 

This should work, but can be quite slow. A preferred approach is found in a paper from HIDRAULICA \cite{bib:hidraulica} and implemented by V5RC team 4253B \cite{bib:4253bmotion}. This approach generates only a specific number of points and uses kinematics to perfectly interpolate between them. Only those points at different stages of the motion (when we reach max velocity, when we reach max acceleration, and so on) are created and stored, then, whenever we request a point between two of these values, we use the starting point and kinematics to find the requested point. This method allows the on-the-fly generation of linear motion profiles. 
\begin{lstlisting}[language=C++]
Point getTimedPoint() {
    timer.start();
    const second_t t{timer.timeElapsed()};
    return getPointAt(t);
}
\end{lstlisting}

We have used a similar method before during Over Under. While this technique is appropriate when there are few disturbances, if the system is not quite linear or experiences external disturbances (as were common during Over Under), the system will be unable to follow the profile and will fall short of its destination. To this end, we also make use of position sampling: instead of basing our current target for the system on time along the profile, we also check \textit{where} along the profile we currently are. This is done via a binary search that finds a close time along the profile that matches our current position. This means that, if the system was blocked or perturbed, it will be able to "catch up" to where it should be. 
\begin{lstlisting}[language=C++]
Point getClosestPoint(const Unit s) {
    // Return appropriate value if behind start or in front of end.
    if(distance(s, start) > Unit{0}) {
        return {start,      
                UnitsPerSecond{0},
                UnitsPerSecondSq{0},
                UnitsPerSecondCb{(isBackwards()) ? -params.maxJ : params.maxJ},
                0_s};
    } else if(distance(s, end) < Unit{0}) {
        return {end,
                UnitsPerSecond{0},
                UnitsPerSecondSq{0},
                UnitsPerSecondCb{0},
                points[6].t};
    }
    const auto [t0, t2] = getTimeBounds(s);
    const second_t t1{searchForClosestPointTime(s, t0, t2)};
    return getPointAt(t1);
}
\end{lstlisting}

Because this would mean the system never begins moving (as at the starting position of the profile, the system should be at standstill), we also find the point it should be at in time and take the max parameters of the two as our current target. 
\begin{lstlisting}
Point getPoint(const Unit s = Unit{0}) {
    Point point{getTimedPoint()};
    if(params.usePosition) {
        const Point closestPoint{getClosestPoint(s)};
        if(abs(closestPoint.v) > abs(point.v)) {
            timer.setTime(closestPoint.t);
            point = closestPoint;
        }
    }
    graphPoint(point);
    return point;
}
\end{lstlisting}

\subsection{Slew Rates}
Slew rates are essentially rate limiters. That is to say, if you were slewing a voltage of 12 to the arms with a rate of 1 V each call. The first call would provide a voltage of 1 V, the second 2 V, the third 3 V, and so on. 

Slew rates were initially popularized in VEX as a way of preventing PTC trips during the Cortex days, since the slower acceleration led to smaller reverse current \cite{bib:sigbotsslew}. To this day, a small amount of slew is applied to motor movements (at least for VEXcode) \cite{bib:vexinbuiltslew}. 

We are more interested in the use of slew rates for general purpose rate limiting. To this end, the applications are potentially vast from finer-tuned controls on the arm or drive, to motion planning applications.
